# PagerLens tutorial video script

**Title:** From alert to confirmed cause: investigating incidents with PagerLens

**Target length:** about 7 minutes 20 seconds as built by `docs/video/build.sh` (the narration is about 970 words, 6 minutes 30 seconds of speech with the Kokoro voices, plus a title card, deliberate pauses over on-screen waits and a short pause after every scene). The timestamps in the scene table below are the original human-pace estimates; the build drives every scene from the measured length of its audio instead (each scene lasts at least its narration plus 0.7 seconds), so the picture matches what is being said.

**Audience:** customers and internal teams (engineers, SREs, solution architects, sales engineers). Assumes people know what an alert and a deploy are. It does not assume they know Postgres, pgvector or MCP; the narration explains each in one sentence.

**Goal:** after watching, the viewer can (1) read the dashboard and an investigation, including the evidence behind each claim, (2) explain the three methods (Rules, AI, Rules + AI), watch an AI investigation run end to end, and see what stops the model from acting on anything, (3) teach PagerLens a confirmed cause and see it recalled, (4) send their own telemetry and connect an editor over MCP, and (5) say where PagerLens fits in the ecosystem and runs on Postgres with pgvector.

Reference: the [guide](GUIDE.md) for every claim made on screen. Nothing in this script needs a live URL: everything runs on `localhost`.

## 1. Prerequisites and seed data (reproducible locally)

Record on a clean machine with Docker and Python 3.11 or newer. Use throwaway values; never show a real password, token or provider key on screen.

```bash
cd pagerlens
cp .env.example .env
# set POSTGRES_PASSWORD in .env to a throwaway value (python3 -c "import secrets; print(secrets.token_urlsafe(24))")
docker compose down -v                 # start from an empty database every take
docker compose up -d db
python3 -m venv .venv && .venv/bin/pip install -e ../agentpg-kit -e ".[dev]"
set -a; . ./.env; set +a
.venv/bin/pagerlens migrate
.venv/bin/pagerlens seed               # five-service demo shop, 12 runbooks, healthy baseline
# DEMO STAND-IN for the AI scene: a deterministic fake OpenAI-compatible server, not a real model (loopback only)
.venv/bin/python scripts/fake_llm.py --port 8099 > /tmp/fake-llm.log 2>&1 &
LLM_BASE_URL=http://127.0.0.1:8099/v1 LLM_API_KEY=demo LLM_CHAT_MODEL=demo-chat EMBEDDING_MODEL=demo-embed \
  .venv/bin/pagerlens serve 2> /tmp/pagerlens-recording.log &   # http://localhost:8000; the setup code is in this log
```

The three `LLM_*` and `EMBEDDING_MODEL` variables define the read-only "Environment (server settings)" provider account that scene 8 uses; they also make retrieval use the stand-in's (lexical, deterministic) embeddings. Run `migrate` and `seed` without them, as above, if you want the built-in offline embedder for those two steps; the server reconciles the vector size on start either way. The stand-in is labelled in its banner and in every answer it gives ("DEMO STAND-IN"); never present it as a real model.

| Item | Value or how to get it |
|---|---|
| Setup code | Printed in `/tmp/pagerlens-recording.log` under "PagerLens first-run setup" (format `XXXX-XXXX-XXXX`); it changes every restart |
| Admin password | Any throwaway of 12 or more characters, chosen during recording (type it off screen or blur the field) |
| Tokens | Create in the app during the recording: one `read` token named `editor` (scene 10) and one `ingest` token named `demo-sender` (scene 9). Export them in the terminal that is on screen as `PAGERLENS_TOKEN` without displaying the value (`export PAGERLENS_TOKEN=...` typed before recording, or run the commands from a script) |
| Demo data | Created by the Lab during the recording. Telemetry timestamps are relative to "now", so always press **Break it** immediately before investigating; a pause of more than about an hour makes the failure window drift out of the investigation's windows |
| AI account | Scenes 7 and 8 use the environment account backed by `scripts/fake_llm.py` (the demo stand-in), so the recording needs no provider key and the AI investigation is reproducible. To show a real model instead, start `pagerlens serve` with a real `LLM_BASE_URL`, `LLM_API_KEY` and `LLM_CHAT_MODEL` (throwaway key, revoked afterwards) and record scene 8 again: the screens read the same, but the wording and the reasoning are the model's, and AI accuracy on live models is not measured (see the guide) |
| Browser | Chrome, 1920 x 1080, light theme, 100% zoom, no extensions, bookmarks bar hidden (the recorder does this for you) |
| Terminal | A second window, large font (18 pt or more), dark background, prompt shortened |

Pre-flight rehearsal (do once, off camera): run `docs/video/record.spec.ts` with `PACE=0.2` (section 4); it asserts the two outcomes the narration relies on. This script was rehearsed end to end that way on 2026-10-27 against a fresh local database and the stand-in model:

- Scenario `bad_deploy` (alert on `checkout-api`, deploy `v2.14.0` two minutes before the failure began): the first hypothesis of the Rules investigation is "Release v2.14.0 of checkout-api introduced the failure" (99% in the rehearsal), with supporting lines for the deploy timing and for the new `NullPointerException in PromoCalculator.apply` signature. No "refutes" line appears for this scenario (scene 5 therefore only points at one if it exists).
- After **Mark resolved** and a second **Break it** on the same scenario, the second report has a "Similar past incidents" section that lists the first incident ("#1 HighErrorRate (checkout-api), resolved as bad_deploy (similarity 1.0)"). The entry shows the confirmed cause and the similarity; it does not show the free-text note, so the narration says "the cause it was confirmed as" and not how it was fixed. The report's evidence list also gains a line "1 similar past incident(s) were resolved as bad_deploy".
- The AI run (scene 8) with the stand-in finishes in about a second, ranks `bad_deploy` first with the source badge "rules + AI" and both scores shown, and the run viewer shows "AI turn" rows.

Wording and numbers on screen are from that rehearsal; scores vary slightly with the seed and timing, so the callouts never quote a percentage.

This is the text of `docs/video/narration.txt`, which is the source of the synthetic voice (Kokoro). It is written for listening: short sentences, one idea each. So there is no extra database to run.

## 4. Recording notes (the Playwright recorder)

`docs/video/record.spec.ts` performs every on-screen action of scenes 1 to 12 in real Google Chrome with Playwright video (1920 x 1080, light theme), at a slow human pace: a visible cursor with click ripples, smooth wheel scrolling, typed text, callout highlights with the callout text from the scene table, the lower thirds, and the end card. Each scene is held for the length of its narration audio plus 1.2 seconds (`NARRATION_TIMING`, written by `docs/video/narration.py`), and the actions inside a scene wait for the start of the sentence they illustrate; without timing every scene lasts the length in the scene table. Narration, captions and the final mp4 come from `docs/video/build.sh` (see `docs/video/README.md`), which runs the whole chain with one command.

**Run it** (or run `docs/video/build.sh`, which does all of this and the narration and final cut)

1. Start the stack as in section 1 (fresh database, `migrate`, `seed`, the stand-in model, `pagerlens serve` with stderr to `/tmp/pagerlens-recording.log`).
2. One time: `cd docs/video && npm install` (installs Playwright 1.64.1; it uses the Chrome already on the machine). Playwright's video recording needs its own ffmpeg: if it is missing, `npx playwright install ffmpeg` downloads it once.
3. `ADMIN_PASSWORD='<throwaway of 12+ characters>' npx playwright test` from `docs/video`. Other variables: `PAGERLENS_URL` (default `http://localhost:8000`), `SETUP_CODE` or `SETUP_LOG` (default `/tmp/pagerlens-recording.log`, polled for the first-run code), `PACE` (default 1; `0.2` is a quick rehearsal), `HEADED=1` to watch.

Nothing secret is stored in the repository: the admin password comes from your environment, the setup code from the log, and the two tokens (`editor` with read access, `demo-sender` with ingest access) are created through the API before the camera starts, kept in memory, and never shown. Sign-in happens before recording too, so the video starts on the Dashboard.

**What it checks while it records** (the run fails if the product and this script disagree)

- The MCP calls of scene 11 are real: `list_incidents` returns the demo incidents, `get_incident` finds an investigated one, and the `add_note` attempt with the read token is refused.
